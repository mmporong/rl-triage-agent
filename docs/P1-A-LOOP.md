# P1-A 실험 선택 고리 설계 (2026-10-09, 초안)

P0-A2에서 텔레메트리만 보는 원인 순위는 고정 규칙과 같거나 못했다. 남는 기여 후보는 **경쟁하는 가설을 가르는 다음 실험을 고르고, 사람 승인 뒤 관측으로 판단을 갱신해 원인을 확정하거나 식별 불가로 끝내는 고리**다([AI-DAY-2026.md](AI-DAY-2026.md) 최소 데모, [CLAUDE-HANDOFF.md](CLAUDE-HANDOFF.md) 5절 P1-A). 이 문서는 구현 전 설계다. 실험 결과·성능 주장은 없다.

## 1. 왜 "계측 probe"인가

- v1 고리는 의심 변경 하나를 되돌려 재학습했다(`eval_bridge.approve`). P0-C의 숨은 결함은 설정 변경이 아니라 되돌릴 대상이 없다. 실제 현장에서도 원인이 코드·자산·프레임워크 쪽이면 "설정 하나 되돌리기"가 실험이 되지 않는다.
- 엔지니어가 실제로 하는 다음 실험은 대개 **계측**이다. 기록된 노이즈와 실제 샘플 노이즈가 같은지, 가치 함수가 수익을 설명하는지, 보상을 상태에서 다시 계산하면 기록값과 같은지, 토크가 포화되는지, 접지 중 발이 미끄러지는지, 에피소드가 설정 길이에서 끝나는지 같은 것들이다.
- probe는 학습을 다시 하지 않고, 실패 실행의 체크포인트를 같은 코드·설정으로 짧게 돌려 측정한다(수십 초~수 분). 재학습보다 GPU 비용이 작아 "실험 수·GPU 분" 주 지표에 맞는다.

## 2. probe 목록 (공개, canonical args 고정)

| probe | 측정 | 정상 기준 | 주로 가르는 범주 |
|---|---|---|---|
| `P_noise` | 학습 경로 `act()` 샘플의 실제 표준편차 ÷ 기록된 `action_std` | ≈ 1 | exploration |
| `P_value` | 롤아웃 수익에 대한 critic 설명 분산 | 기준 실행과 비슷 | optimizer |
| `P_reward` | 상태에서 문서 정의대로 다시 계산한 추종 보상 항(`track_lin_vel_xy_exp`, `track_ang_vel_z_exp`)과 기록값의 상대 오차. 패널티 항은 보지 않는다 | ≈ 0 | reward(추종 항 구현) |
| `P_torque` | 낮은 관절 속도에서 토크 포화 비율 | 기준 실행과 비슷 | actuator |
| `P_slip` | 접지 중 발 수평 속도 | 기준 실행과 비슷 | physics |
| `P_episode` | 시간 제한 종료가 난 스텝 ÷ `episode_length_s / step_dt` | ≈ 1 | termination |

각 probe의 예상 signature(범주별로 어느 쪽으로 움직이는지)와 판정 임계값은 평가 전에 커밋한다. 임계값은 정상 실행(NONE)과 v1 dev 결함으로 정하고 P0-C holdout에는 맞추지 않는다.

**설계자 정보:** probe 목록은 P0-C 숨은 결함을 만든 사람이 썼다. 각 probe가 숨은 결함 하나를 직접 겨누므로, P0-C에서 "probe로 원인을 찾았다"는 것은 고리가 동작한다는 확인일 뿐 일반화 근거가 아니다. 일반화 주장에는 probe 설계자가 모르는 결함이 필요하다(IMPLEMENTATION-ORDER 2절 F, 공개 이슈로 원인이 확정된 결함).

## 3. 고리

1. 진단: 텔레메트리로 범주 순위를 낸다(에이전트 또는 규칙).
2. 가설 2~3개와 각 가설이 예측하는 probe 결과를 사전등록한다(가설, 예상·반증 signature, 실패 실행 tag, 체크포인트 SHA256, 기준 실행 SHA256).
3. 실험 선택: 상위 가설들이 서로 다른 결과를 예측하는 probe 중 비용이 작은 것을 고른다. 확률·EIG는 쓰지 않는 휴리스틱이다.
4. 승인: 사람이 CLI로 승인하거나 거절한다. 승인은 사전등록 digest·probe 이름·canonical args·예산에 묶이고 한 번만 소비된다. 같은 실험을 다시 요청하면 새 승인이 필요하다. 원장은 잠금 파일로 줄 단위 쓰기를 보호하고, 상태를 바꾸는 호출(승인·소비)은 한 프로세스에서 한다. 가설이 하나 남으면 그 범주의 확정 probe를 요청한다(`next_probe`).
5. 실행: 브리지가 probe를 Isaac에서 돌리고 receipt(입력 SHA, 출력, 시간, 종료 코드)를 남긴다. timeout이나 불명 결과는 실패로 단정하지 않고 "불명"으로 둔다.
6. 갱신: 관측이 사전등록한 예상과 맞으면 그 가설을 유지하고, 반증 signature면 기각한다. 남은 가설이 하나이고 그 가설의 확인 probe가 맞으면 "확정", 예산이 끝나도 둘 이상 남으면 "식별 불가"로 끝낸다.
7. 회복 확인(선택): 확정된 원인을 고친 학습(P0-C에서는 결함 없는 코드)을 고정 평가로 판정한다. 회복만으로 유일 원인을 확정하지 않는다.

## 4. 비교 (P0-C holdout에서, 평가 전에 커밋)

| 선택 방식 | 설명 |
|---|---|
| 전수 | probe 6개를 모두 돈다(상한 비용) |
| 고정 순서 | 엔지니어 체크리스트 순서 |
| 무작위 | seed 고정 무작위 순서 |
| 규칙 + 가르기 | P0-A2 규칙 순위 상위 가설을 가르는 probe |
| 에이전트 + 가르기 | 에이전트 순위 상위 가설을 가르는 probe |

같은 체크포인트·seed에서 probe 결과는 순서와 무관하므로, holdout 실행마다 probe 6개를 한 번씩 재서 결과표를 만들고 다섯 방식은 그 표 위에서 돌린다(`probe_loop.simulate`). 데모의 사람 승인 고리는 같은 갱신 규칙을 원장과 함께 실제로 돈다.

주 지표는 확정까지 probe 수·GPU 분·틀린 확정 수·식별 불가 수다. 사람 승인 시간과 모델 토큰은 따로 기록한다. 표본은 holdout seed 3 × 결함 6 = 18칸이고 유의성은 주장하지 않는다.

## 5. dev 측정과 정의 수정 (2026-10-09)

seed 7 보정 실행(NONE, F1~F5, F6 5%)에서 probe를 처음 쟀다(`evals/results/p1a_probes_dev_20261009/`, 이 절 아래 정의로 바꾸기 전 측정). 사전 임계값으로는 F1(`P_reward` 0.37), F2(`P_torque` 0.066), F3(`P_noise` 0.049), F6(`P_episode` 0.05)이 해당 probe에서 abnormal이었고, NONE은 6종 모두 normal이었다. 문제가 셋 나왔다.

- `P_value` 설명 분산이 NONE에서도 −0.13이었다. 정상 실행은 수익 분산이 작아 설명 분산이 흔들린다. 판정 지표를 상대 가치 오차(mean|R−V| ÷ mean|R|)로 바꾸고, 임계값은 NONE의 2배 초과(바닥 0.05)로 정했다.
- `P_slip` 접지 발 속도가 F5(마찰 0.25배)에서 0.768로 NONE 0.741과 같았다. 1N 기준 접지가 발-스텝의 91%를 잡았다. 하중을 실은 접지(수직력 10N 이상)의 접선력/수직력 95% 분위로 바꿨다(쿨롱 한계라 마찰이 작으면 작아진다). 임계값은 NONE의 절반 미만이다.
- F3(탐색)에서 `P_torque`도 abnormal(0.476)이었다. 탐색 결함일 때의 `P_torque` 예상을 normal에서 "예상 없음"으로 바꿨다. 그대로 두면 순서에 따라 참 가설을 잘못 기각한다.

2차 dev 측정(`evals/results/p1a_probes_dev2_20261009/`)에서 다시 두 문제가 나왔다.

- 마찰 사용률이 NONE 포함 모든 실행에서 1.3×10⁻⁷이었다. Isaac Lab 접촉 센서 `net_forces_w`에 접선력이 거의 없어 잴 수 없는 지표였다. 하중 접지(수직력 10N 이상) 중 발 수평 속도로 바꾸고, 임계값은 NONE의 3배 초과(바닥 0.01 m/s)로 정했다.
- 상대 가치 오차는 NONE 0.106에 결함 6종 모두 0.62~3.46이었다. 학습이 망가지면 원인과 상관없이 커지는 지표라 optimizer만 가리키지 못했다. 그 결과 F1은 참 가설이 기각됐고 F5는 optimizer로 잘못 확정됐다. critic 출력과 실제 수익의 상관으로 바꾸고, 임계값은 NONE의 절반 미만으로 정했다.

이 수정은 설계자가 결함을 아는 상태에서 dev 결함을 보고 한 것이다. holdout(seed 2026~2028)은 수정 전후 모두 재지 않았다. 수정한 정의는 다시 dev에서 재서 기록하고, 그 뒤 holdout에 한 번 적용한다.

## 6. 구현 순서

1. probe 레지스트리·사전등록·승인 원장·receipt·갱신 규칙(파이썬, GPU 없음)과 테스트. 승인 중복 소비·불명 결과·재시작을 테스트한다.
2. probe 6개의 Isaac 스크립트(체크포인트 롤아웃 계측). NONE·결함 1개씩 짧게 돌려 측정값이 나오는지 확인한다.
3. 임계값을 NONE과 v1 dev로 정해 커밋한다.
4. P0-C holdout에서 4절 비교를 돌린다.
5. 데모: 결함 하나로 진단 → 사전등록 → 거절/승인 → probe → 갱신 → 확정 → 회복 확인을 trace와 함께 보인다.
