# 원인 확인 검사와 네 방식의 실행 비용

이번 비교에서 네 방식의 전체 원인 확인율은 같았고, 회복한 정책은 없었다. 구현한 기능은 모터 함수와 PPO 갱신 불변식을 구분하는 검사, 불충분한 근거로 교정을 열지 않는 분기, 조사와 교정을 조회·재개하는 CLI다. 이 결과로 모델이나 반복 에이전트의 우위를 주장하지 않는다.

## 입력과 비교 단위

새 학습 원천은 Go2 정상·보상 좌표계 결함·모터 함수 결함·보상과 PPO epoch 복합 결함·물리 결함을 포함한다. 결함 종류는 설계자가 이미 알던 종류다. 새 seed와 새 체크포인트를 썼다는 사실을 처음 보는 결함에 대한 일반화로 해석하지 않는다.

| 구간 | 등록 범위 | 실제 기록 |
|---|---|---|
| 공통 원천 | 학습 20회, 고정 26조건 평가 20회 | SDK 40회 |
| 진단 비교 | 모터 2·복합 2·물리 2사례, 네 방식 | 6사례 × 4방식 = 24행 |
| 교정과 평가 | 모터 2·복합 2사례, 네 방식 | 4사례 × 4방식 = 16행 |
| 정상 host gate | 앞선 중단 판의 정상 입력 | 2사례 × 4방식, 모델 호출·검사 제안 전에 차단 |

정상 host gate는 모델의 정상 판별과 구분한다. 앞선 중단 판의 정상 행을 뒤의 6사례 진단 분모에 합치지 않는다. 교정 결과의 16행에는 과거에 완료한 모터 효과 8개를 검증해 가져온 행과 새 epoch 교정 효과 7개, 원래 진단에서 보류된 1개가 있다. 같은 효과를 재학습하거나 서로 다른 방식의 실행으로 복제하지 않았다.

원천: [학습·평가 묶음](../evals/results/lineage_source_s2660_s2669_20261104_v1/) · [진단 결과](../evals/results/diagnostic_comparison_s2664_s2669_20261104_v4/summary.json) · [교정 결과](../evals/results/recovery_comparison_s2664_s2667_20261105_v13/summary.json).

## U1: 증상과 원인 확인을 구분한다

토크가 달라졌다는 관측만으로 모터 고장을 확정하지 않는다. 정책이나 PPO 갱신 오류도 토크의 차이를 만들 수 있다. 새 runtime 프로파일은 아래 세 검사를 노출하며, 각 검사는 확인한 범위만 반환한다.

| 검사 | 확인하는 불변식 | 확인하지 않는 것 |
|---|---|---|
| `P_actuator_mapping` | 등록된 속도 격자에서 DCMotor 토크 제한 함수와 설정 | 모든 모터 결함, 정책 전체 정상 |
| `P_optimizer_count` | 짧은 실행의 실제 optimizer step과 미니배치 수 | 과거 학습의 모든 갱신 이력 |
| `P_optimizer_gradient` | PPO clipped-surrogate 계산의 gradient | 모든 PPO 구현 오류 |

이 검사는 원천의 등록 메커니즘을 새 실행에서 재현한다. actuator 검사는 정책 추론 없이 함수를 읽고, optimizer 검사는 초기화한 짧은 실행을 쓴다. 체크포인트 SHA는 원천 식별에 결합하지만 검사에서 가중치를 로드하지 않는다. 이를 과거 정책의 내부 상태를 검증한 것으로 쓰지 않는다.

개발 대조의 실제 SDK 실행은 정상 함수, F2 함수, PPO 갱신 횟수 오류, inverse-ratio 계산 오류의 네 가지였다. 모터 두 건은 부모 정규화기를 고친 뒤 같은 보관 원문으로 재검증했으므로 새 GPU 실행이나 보류 평가가 아니다.

## 진단 결과

| 방식 | 전체 원인 집합 확인 | 부분 확인 | 확인 없음 | HOLD |
|---|---:|---:|---:|---:|
| 고정 순서 | 2/6 | 2 | 2 | 0 |
| 명시 규칙 | 2/6 | 2 | 2 | 0 |
| 같은 모델 단일 계획 | 2/6 | 2 | 2 | 0 |
| 관측 후 반복 에이전트 | 2/6 | 1 | 1 | 2 |

전체 원인 집합 확인은 모터 두 사례에서 나왔다. 복합 결함의 PPO epoch를 확인한 결과는 실제 결함 하나를 맞힌 부분 확인이다. 이를 오진이나 복합 결함 전체 해결로 바꾸지 않는다. 물리 결함은 새 세 검사로 원인을 확인하지 못했다.

반복 에이전트의 보류 중 하나는 앞서 수행한 gradient 검사를 다시 선택해 host 계약이 거부한 사례다. 이때 원래 프롬프트가 반복 선택 금지를 명시했다고 쓰지 않는다. 모델의 선택과 host의 거부를 분리해 기록했다.

## U2: 행동 실패가 추가 교정 권한이 되지 않는다

교정 뒤에는 새 체크포인트의 고정 평가, 실제 교정 기록, 확인 검사의 범위를 다시 검증한다. 행동이 기준에 미달하더라도 새 원인이 확인되지 않으면 추가 교정을 승인하지 않는다. 상대 기준만 통과한 정지 정책을 정상으로 받지 않도록 절대 추종·낙상 조건도 적용한다.

| 방식 | 회복 | 미회복 | 진단 HOLD로 교정 없음 |
|---|---:|---:|---:|
| 고정 순서 | 0/4 | 4 | 0 |
| 명시 규칙 | 0/4 | 4 | 0 |
| 같은 모델 단일 계획 | 0/4 | 4 | 0 |
| 관측 후 반복 에이전트 | 0/4 | 3 | 1 |

복합 결함에 대한 새 epoch 교정 7회는 학습과 고정 평가를 모두 마쳤다. 첫 세 갱신의 optimizer step은 모두 20회로 복원됐지만, 행동 평가에서는 회복하지 못했다. 보상 좌표계 구성은 보존했다. 사후 검토는 `failure_without_confirmed_cause`로 남기고 추가 원인 확인을 요구했으며, 자동 교정 권한은 만들지 않았다.

| 복합 원천 | 동일 seed에서의 교정 후 체크포인트 | 선형 속도 RMSE, m/s | yaw RMSE, rad/s | 낙상 |
|---|---|---:|---:|---:|
| case-07, 새 실행 3개 | `f9757ba4…` | 1.184223 | 0.633354 | 0 |
| case-08, 새 실행 4개 | `5f987bf2…` | 1.193473 | 0.631187 | 0 |

같은 원천·재학습 seed·교정 설정을 쓴 방식들은 같은 체크포인트 SHA를 만들었다. 이 분모에서 선택 방식에 따른 회복 차이는 관측되지 않았다. 낙상이 없다는 결과는 명령을 잘 따른다는 뜻이 아니다. 이번 실패를 외란에 날아가거나 넘어진 뒤 일어나지 못한 사례로 설명하지 않는다.

[별도 post 확인](../evals/results/post_actuator_confirmation_s2664_20261105_v1/)은 SDK 1회로 12개 관절의 모터 함수가 정상이고 검사 전 상태가 복원됐음을 확인했다. [세부 관측](../evals/results/post_actuator_observation_s2664_20261105_v1/observation.json)에 함수 확인과 재사용한 행동 수치를 나눠 두었다. 기존 교정 후 고정 평가의 선속도 RMSE는 후보 0.184067m/s, 참조 0.153728m/s로, 상대 비율 1.197352가 등록 상한 1.1513을 넘었다. 두 정책은 절대 행동 조건을 통과했다.

호스트는 `reference_review_required`를 반환했다. 추가 교정 제안·승인·권한 생성은 모두 false이고, 미관측 PPO 두 검사는 unknown으로 남겼다. 기존 행동 수치를 재사용했으며 새로 측정한 것은 정책 가중치를 로드하지 않는 모터 함수다. 기존 `not_recovered`를 새 회복으로 바꾸지 않았다.

이 별도 확인의 부모 경과는 153.215715초, 그 안의 owned 구간은 153.172초였다. 실제 Simulator 자식의 owned wall은 13.797초였고 부모 owned 구간과 더하지 않는다. API 호출은 없었다. 등록된 승인 영수증의 주체·요청·원천 SHA를 outer와 Git 소스에 고정하고 한 번만 소비했다. 이는 호스트 위임 기록이며 암호학적 로그인 인증이나 별도 사람이 수행한 승인이라는 뜻은 아니다.

## U3: 한 CLI에서 제안·승인·결과를 관리한다

```powershell
cd "$HOME/rl-triage-agent"
.\.venv\Scripts\python.exe -m rl_triage.investigate_v3 --help
```

조사 명령은 `prepare`, `next`, `approve`, `dispatch`, `settle`, `status`, `export`다. 같은 진입점의 `recovery-*` 명령으로 교정 요청, 별도 승인, 학습·평가, 후속 검토를 다룬다. 모델은 검사 ID와 fact ID를 고르고, host가 인자와 권한을 검증한다. 승인된 요청은 한 번만 소비하며 중단된 요청은 원래 실행 증거로 접수하거나 unknown으로 닫는다.

`status`는 모델의 HOLD와 실행 원장의 미접수 요청을 구분한다. 조사 export와 회복 결과 조회는 같은 CLI의 서로 다른 명령이며, 모든 기존 실행기가 하나의 export 형식으로 바뀐 것은 아니다. 새 runtime 세 검사와 기존 여섯 검사의 지원 범위도 구분한다.

`post-status --session evals/results/post_actuator_confirmation_s2664_20261105_v1`은 같은 진입점에서 커밋된 모터 후속 확인을 조회한다. 파일·manifest SHA와 Git HEAD blob을 검증하며 API·SDK 실행 없이 저장 결과를 반환한다. 새 측정으로 표시하지 않는다.

사용법과 승인 경계: [등록 조사 CLI](REGISTERED-DIAGNOSTIC-RUNTIME.md).

## 실패·재개·공통 비용

공통 원천 확보는 한 번만 센다. 부모 경과 11,065.078초 안에 SDK owned wall 10,691.327초가 들어 있다. 장치 에너지 228.920119Wh도 공통 원천 구간의 관측이며 네 방식에 반복 가산하지 않는다.

교정 비교의 primary는 실패 이력을 포함해 SDK 32회를 사용했다. 그중 마지막 V13 배치는 새 SDK 14회로 효과 7개를 완료했다. 이전 폴더·종료 증거·로그 이름 오류와 중단된 학습 비용은 별도 이력으로 보존했다. 별도 post 1회는 primary 32회에 포함되지 않으며, 승인된 합계 상한은 33회다.

primary 원장에서 확인된 비중첩 wall의 하한 합은 29,323.430740초다. 전체 경과 합은 누락 구간 때문에 null이다. 이 하한은 네 방식의 평균 실행 시간이나 한 번의 사용자 작업 소요 시간으로 쓰지 않는다. 중첩 owned/phase 구간, 공동 원천, 같은 실행 영수증을 중복 가산하지 않는다.

과거 모터 효과 8개의 실행 순서가 등록 rotation을 소비하지 않은 차이가 있었다. 원래 결과를 보존하고 이후 생성기를 고쳤다. 이 역사 구간을 균형 순서의 통제된 속도·에너지 우위 근거로 사용하지 않는다. 새 V13의 원래 HOLD도 결과를 본 뒤 다시 호출하지 않았다.

[전체 비용 원장](../evals/results/mechanism_resource_whole_study_20261105_v1/summary.json)은 primary와 별도 post를 분리해 합친다. primary 하한에 post 부모 경과를 한 번 더하면 29,476.646456초다. 실행 전 순차 CPU 확인 두 구간 111.875047초까지 포함한 알려진 하한은 29,588.521503초이며, 누락된 준비·대기 때문에 완전한 합계는 여전히 null이다. 이 값은 방법 하나나 사용자 작업 한 번의 시간으로 해석하지 않는다.

post sampler는 장치 표본 73개를 수집했다. 148.091833초 표본 창의 coverage는 99.9653%, 장치 에너지는 1.676219Wh, 관측 최대 전력은 43.01W, 메모리는 3385MiB였다. 부모 전체 구간을 덮지 않고 다른 부하를 포함하므로 전체 프로젝트 에너지나 프로세스 비용으로 가산하지 않는다.

공통 원천: [별도 비용 집계](../evals/results/source_common_cost_s2660_s2669_20261104_v1/summary.json). 캠페인 SDK 146회는 개발·smoke 7, 원천 40, 중단된 진단 13, 현재 진단 53, 교정 이력과 별도 post 33으로 구분한다. 이 프로젝트 전체 횟수를 교정의 과학 분모 16행과 섞지 않는다.

- [NVIDIA SMI](https://docs.nvidia.com/deploy/nvidia-smi/): 사용률·전력·장치/프로세스 메모리와 지원되지 않는 값을 구분한다. owned wall을 GPU kernel 시간으로 바꾸지 않는다.
- [NVML 장치 조회](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html): 동적인 process 목록과 장치 표본의 범위를 확인하는 데 사용했다.

이전 릴리스의 회복 시연과 새 비교는 분모가 다르다. 기존 성공을 이번 비교의 성공으로 가져오거나, 이번 미회복으로 과거 성공 원문을 바꾸지 않는다. 외부 사용자 미주입 실패, 사람의 발표 리허설, 현장 AV 확인은 이 실험이 검증한 항목에 포함하지 않는다.
