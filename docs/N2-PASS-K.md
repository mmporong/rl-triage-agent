# 결정 반복 일관성(pass^k)과 비용

이미 본 결정 packet을 같은 모델·temperature 0으로 반복해 두 가지를 기록한 개발 측정이다. 하나는 진단(첫 판단)·교정 제안 결정이 매번 같은가이고, 다른 하나는 그 비용이다. 결정적 기준선을 같은 표에 둔다.

**핵심: 단일 호출의 유효 출력은 반복 내내 결정이 같았고, pass^k를 낮춘 것은 계약 위반 출력 6/55다.**
- 유효 출력 49회: 11개 packet·종류 모두 packet마다 결정이 하나였다.
  - 진단 27회는 모두 continue · reward다.
  - 교정 22회는 모두 propose · 등록 교정 · restart다.
- 계약 위반 6회는 두 종류다.
  - 진단 3/30: 근거 claim이 빈 결정 2, 카탈로그와 다른 expected_outcomes 1
  - 교정 3/25: 같은 바이트의 깨진 JSON 3

범위는 다음과 같다.
- **입력:** 시연 seed 2030·2031·2033·2034·2040과 E4b 개발 입력 h02_s2027의 packet이다. 모두 이미 본 입력이다.
- **새 측정은 단일 호출뿐이다.** packet마다 5회, 모두 55회다. NAT v4 반복은 사전등록 전에 본 E4b v4 기록(같은 packet 5회)을 다시 읽었다.
- **출력 형식만 바꾼 구조화 출력 arm(55회)을 따로 사전등록해 쟀다.** 사전등록 개선 기준에 못 미쳤고 채택하지 않는다(아래 "구조화 출력 arm").
- **주장하지 않는 것:** 진단 정확도, 다른 방법 대비 우위, 일반화, 토큰·시간·GPU 절감.

pass^k(결정 일치)는 k개 실행을 비복원으로 뽑았을 때 모두 계약상 유효하고 같은 결정일 확률이다(packet 평균). 무효 출력도 pass^k를 낮춘다. 단일 호출의 varied 판정은 결정이 바뀌어서가 아니라 무효 출력 때문이다.

사전등록 문구(요약 파일 그대로):
- "단일 호출 진단: 같은 packet 반복에서 결정이 흔들렸다. 흔들린 packet과 결정 분포를 그대로 공개한다."
- "단일 호출 진단: 평균 pass^4가 사전등록 하한 0.8 미만이라 다음 시연 결정 단계에 쓰기 전에 재검토한다."
- 교정도 같은 두 문구다.
- 공통: "이미 본 packet(시연·개발 입력)을 같은 모델·temperature 0으로 반복한 개발 측정이다. 반복 일관성은 정확도의 근거가 아니고, 결정적 기준선은 같은 입력에서 늘 같으므로 pass^k가 1이다. NAT 반복은 사전등록 전에 본 E4b v4 기록을 다시 읽었다. 비용은 토큰·벽시계·계산 시간 기록이며 절감 주장이 아니다."

**무엇이 흔들렸나**
- [사실] 계약 위반 6/55
  - 진단 3/30: 근거 claim이 빈 결정 2회(seed 2031·2040), 선택 probe의 카탈로그 기대 결과와 다른 expected_outcomes 1회(h02_s2027)
  - 교정 3/25: 깨진 JSON 3회. 모두 모터 교정 packet(seed 2031 1회, 2033 2회)이다. 세 응답이 같은 바이트였다(체크리스트 객체를 `]`로 닫음)
- [사실] NAT v4 첫 판단은 seed 2031 packet에서 5회 모두 유효했지만 1위가 reward 3 · optimizer 1 · termination 1로 갈렸다.
- [사실] temperature 0에서도 같은 packet에 다른 출력이 나왔다. 단일 호출은 유효·무효가 섞였고, NAT는 1위가 달랐다.
- [추론] 그 원인(제공자 쪽 비결정성, 배치 차이 등)은 이 측정으로 가르지 못한다.
- [추론] 단일 호출 시연은 결정 단계가 호출 한 번이고 의미 재시도가 0이다. 무효 출력이 나오면 사전등록 범주 `model_invalid`로 끝난다. 이번 무효 6/55는 그 위험이 실제로 있음을 보인다. 다만 이미 본 packet 11개의 개발 측정이다.

## 사전등록

- 프로토콜 `bench/protocols/n2_pass_k_v1.json`(`c392360`, LF SHA256 `decb3d51…`)
- 실행기·요약기 `evals/n2_pass_k.py`, 테스트 `tests/test_n2_pass_k.py`
- 모델 `nvidia/nemotron-3-super-120b-a12b`, temperature 0, `reasoning_effort: none`
- 단일 호출
  - packet마다 5회를 부른다.
  - run 번호를 바깥 반복으로 두어 같은 packet 호출을 시간에 흩었다.
  - 인프라 오류만 같은 run으로 1회 재시도한다. 이번에는 재시도가 없었다.
  - 요청 상한은 80이다. 계획한 55회를 썼다.
- NAT v4: 새 호출 0. E4b v4 공개 요약의 실행별 기록을 쓴다.
  - 시연 packet을 NAT로 반복하지 않았다. NAT 1회가 LLM 요청 7~9회라 상한 안에서 5회 반복을 맞출 수 없다.
- 결정 키: 진단은 행동과 1위 가설, 교정은 결정·교정·회복 방식
- pass^k(결정 일치) = Σ_g C(c_g,k)/C(n,k)
  - n은 인프라 오류를 뺀 실행 수, c_g는 결정 키가 g인 유효 실행 수다.
  - τ-bench pass^k의 일관성 판이다. k=1이면 유효율이다.
- 사용 판정: 경로·종류마다 packet 평균 pass^4가 0.8 이상이면 다음 시연 결정 단계에 계속 쓰고, 미만이면 쓰기 전에 재검토한다. 이미 끝난 시연 결과는 바꾸지 않는다.

## 같은 packet 짝 비교(단일 호출 대 NAT v4)

| packet | 단일 호출 pass^1/2/4/5 | NAT v4 pass^1/2/4/5 |
|---|---|---|
| h02_s2027 진단 | 0.8 / 0.6 / 0.2 / 0 | 0.6 / 0.3 / 0 / 0 |
| f2_s2031 진단 | 0.8 / 0.6 / 0.2 / 0 | 1 / 0.3 / 0 / 0 |
| f2_s2031 교정 | 0.8 / 0.6 / 0.2 / 0 | 1 / 1 / 1 / 1 |

- 두 경로는 조건이 다르다.
  - NAT는 근거를 도구로 나눠 조회하고 제출 전 점검으로 고칠 수 있으며, 실수 사실을 6자리 문자열로 받는다.
  - 단일 호출은 packet 전체를 한 번에 받고 점검 단계가 없다.
- 시점도 다르다. NAT 기록은 사전등록 전에 본 값이고, 단일 호출 반복은 이 프로토콜 뒤의 새 측정이다. 같은 조건 비교로 쓰지 않는다.
- [사실] seed 2031 진단: 단일 호출은 유효 4회의 1위가 모두 같았다. NAT는 5회 모두 유효했지만 1위가 갈렸다.
- [사실] seed 2031 교정: NAT는 5/5 같은 결정이었다. 단일 호출은 1회가 깨진 JSON이었다.

## 구조화 출력 arm(출력 형식만 변경)

N2와 같은 11개 packet × 5회 단일 호출에서 출력 형식 하나만 바꿨다. 요청에 `response_format`(strict json_schema)을 더했고, 모델·temperature 0·`reasoning_effort: none`·프롬프트 본문·계약 검증기는 같다.

- 사전등록: `bench/protocols/n2_structured_v1.json`(`8960da6`, LF SHA256 `98a42990…`)
- 실행기: `evals/structured_model_call.py`·`evals/n2_structured.py`
- 결과: `evals/results/n2_structured_v1/summary.json`
- schema는 구조만 정했다(필드·필수·형·추가 필드 금지). 의미 규칙은 넣지 않아 기존 검증기가 그대로 센다.
- 지원 확인: 공식 문서로는 확인하지 못했다.
  - NIM 문서는 `nvext.guided_json`만 다룬다.
  - 호스팅 모델 API 참조에는 두 파라미터가 없다.
  - 그래서 평가 packet이 아닌 합성 최소 입력 호출 2회로 서버가 schema를 강제함을 확인했다.

| | 무효(문법 · 계약) | 평균 pass^4 진단 · 교정 |
|---|---|---|
| N2 단일 호출(형식 없음) | 6/55(3 · 3) | 0.60 · 0.64 |
| 구조화 출력 arm | 37/55(0 · 37) | 0.00 · 0.60 |

**문법 무효는 0이 됐지만 계약 위반이 6/55에서 37/55로 늘었다. 이 방식은 시연 결정 단계의 무효 대비책으로 채택하지 않는다.**

사전등록 판정 문구(요약 파일 그대로):
- "출력 형식만 바꾼 구조화 arm은 사전등록 개선 기준(무효 ≤ 1/55, 진단·교정 평균 pass^4 ≥ 0.8)을 넘지 못했다: 무효 37/55(문법 0, 계약 37), 평균 pass^4 진단 0.00·교정 0.60. 개선을 주장하지 않는다."
- "구조화 arm에서 문법 무효(JSON 파손)는 0이었다. 계약 위반은 따로 센다."

[사실] 형식 제약 아래에서 바뀐 출력 내용:
- 키 순서
  - 진단 무효 29/30은 모두 expected_outcomes가 카탈로그와 달랐다.
  - 30회 모두 순위 상위 3은 reward · actuator · exploration이었다.
  - 그런데 29회는 expected_outcomes 키를 알파벳순 첫 세 메커니즘(actuator · exploration · optimizer)으로 적었다.
  - 같은 packet의 N2 단일 호출은 29/30이 순위 상위 3을 키로 썼다.
- 인용
  - 교정 무효 8/25는 모두 근거 인용에 facts에 없는 `registry`를 넣었다.
  - packet별로는 seed 2031 5/5, seed 2033 3/5다. seed 2030·2034·2040 교정은 5/5 유효였다.
- 제안 probe: 진단 30회 중 P_episode가 7회였다(N2 유효 27회 중 1회).
- 문법: 모터 packet의 같은 바이트 JSON 파손(N2 3회)은 사라졌다.
- 결정 키: 유효 결정의 결정 키(진단 행동·1위, 교정·회복 방식)는 N2와 같았다.
- 비용: 입력 토큰은 같았다. 출력 토큰 중앙값은 진단 130~141, 교정 128~162다(N2 156~198, 157~174).

[추론] 형식 제약이 출력 내용(키 순서·인용·제안 probe)을 바꾼 것으로 본다. 그 경로는 이 측정으로 가르지 못한다. 서버 쪽 제약 디코딩이 키 생성 순서에 영향을 줬을 수도 있고, 모델 쪽 생성이 달라졌을 수도 있다. 원시 응답은 비공개 기록에 있다.

## 해석 경계

- 반복 일관성은 결정이 맞다는 뜻이 아니다. 모터 packet에서 단일 호출 결정은 매번 같았지만 1위는 등록 결함과 달랐다.
- packet 6개(진단)·5개(교정)의 평균이다. 표본이 작아 하한·신뢰구간을 붙이지 않는다.
- 무효 출력의 모양은 사실이다. 그 원인(모델 출력, 제공자 디코딩)은 가르지 못한다. 원시 응답은 비공개 기록에 있다.

## 사전등록과 다른 점

실행·판정 절차에서 사전등록과 다른 점은 없다. 55회 모두 첫 시도에서 기록이 남았고 인프라 재시도는 없었다.

## 주장하지 않는 것

- 진단 정확도, 다른 방법 대비 우위, LLM과 규칙의 우열. 이미 본 packet이고, 결함·규칙·probe를 같은 설계자가 만들었다.
- 일반화. packet 11개의 반복 기록이다.
- 토큰·시간·GPU 절감. 비용은 기록값이고 자원이 다르다.
- NAT와 단일 호출을 같은 조건으로 비교했다는 말
- 교정 결정과 등록 규칙의 일치를 독립 판단으로 쓰는 것
- 이미 끝난 시연 결과의 변경. 재검토 판정은 다음 시연 결정 단계에 적용한다.
