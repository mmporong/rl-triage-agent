# 실제 개발 작업에 쓸 수 있는가

이 도구의 대상 사용자는 Isaac Lab으로 로봇 정책을 학습하는 개발자다. 실패한 학습을 다시 시작하거나 설정을 바꾸기 전에, 다음에 확인할 검사 하나와 그 근거를 제시한다. 공개 실험은 정해진 Go2 task와 여섯 검사에 한정한다. 고객의 작업 시간, 구매 의사, 사람 검토 비용, 다른 task의 진단 성능은 아직 측정하지 않았다.

코드 테스트 통과, 실행 기록의 무결성, 판단 변화, 올바른 원인 식별, 정책 회복은 서로 다른 결과다. 판단 변화가 확인돼도 원인을 맞혔거나 정책을 고쳤다는 결론으로 옮기지 않는다.

## 개발자 검토 질문

| 확인할 것 | 질문 | 남길 기록 |
|---|---|---|
| 문제의 빈도 | 최근 실패한 학습 하나에서 무엇을 확인했고 어떤 순서로 판단했는가? | task·실패 조건·사용한 자료·실제 검사 순서 |
| 바뀐 결정 | 검사 전후에 우선 가설과 다음 행동이 무엇이었는가? | 두 판단의 원문과 이를 바꾼 측정값 |
| AI의 필요성 | 같은 자료와 검사 예산을 가진 고정 순서 또는 저렴한 검사 우선 방식으로도 같은 결정을 할 수 있는가? | 각 방식의 완료·보류 상태와 별도 실행 비용 |
| 검토 부담 | 제안의 근거를 확인하고 승인 또는 거절하는 데 얼마가 드는가? | 사람 검토 시간과 거절 이유; 자동 승인 문자열로 대체하지 않음 |
| 불필요한 검사 | 정상 입력, 자료 부족, 지원 밖 입력에서 무엇을 실행했는가? | 검사 수·모델 호출 수·보류 이유·잘못된 확정 여부 |
| 도입 조건 | 로그·설정·체크포인트를 준비하고 실행 환경을 연결할 수 있는가? | 신규 설치 성공 여부·막힌 단계·준비 시간 |
| 데이터 처리 | 모델 API에 보낼 수 있는 자료와 로컬에 남겨야 할 자료는 무엇인가? | 전송 항목·익명화 범위·조직 승인 조건 |
| 책임과 통제 | 실행 가능한 검사, 시간 예산, 승인 주체, 승인 소비 기록을 검토할 수 있는가? | 요청·승인·receipt 연결; 운영자 승인과 사람 신원 인증 구분 |
| 구매 조건 | 사용자와 예산 승인자는 누구이며 기존 분석 방식의 비용은 얼마인가? | 현재 대안·예산·가격 제시 뒤 행동; 선호 발언과 구매 행동 구분 |
| 확장 조건 | 현재 검사로 가를 수 없는 가설에는 어떤 새 관측이 필요한가? | 새 검사 제안과 평가 전 등록; 기존 결과를 고쳐 새 성과로 사용하지 않음 |

외부 검토 결과를 아직 얻지 않았다. 이 질문표는 검토 준비물이며, 사용자 인터뷰나 파일럿의 성과가 아니다.

## 비교 시험의 조건

새 사용자 입력을 평가할 때는 task·자료·검사 예산·완료 조건·원인 판정 방법을 결과를 보기 전에 등록한다. 같은 실패 입력으로 기존 작업 방식과 에이전트를 비교하고, 실패·누락·보류도 분모에 남긴다. 동일한 완료 조건을 만족한 작업끼리 시간과 비용을 비교한다. 빠르게 보류한 실행을 완료한 진단보다 저렴한 성공으로 세지 않는다.

원인 확인에는 결과와 독립된 근거가 필요하다. 정책 회복을 평가하려면 별도로 승인한 개입과 고정 행동 평가를 등록한다. 현재 판단 갱신 실험에는 재학습이나 수리가 포함되지 않는다.

새 사용자 입력, 사람 검토, 가격을 제시한 파일럿은 아직 미실행이다. 기존 실험의 결과와 섞지 않으며, 자료 공유나 외부 연락은 해당 작업의 허용 범위를 확인한 뒤 진행한다.
