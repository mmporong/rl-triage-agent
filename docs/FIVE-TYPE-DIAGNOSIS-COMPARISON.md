# 다섯 유형 진단 정책 비교

Mollet은 독립 원천 10건에 다섯 진단 정책을 적용해 50행을 모두 종결했다. 결함 사례 여덟 건에서 원인군을 올바르게 확정한 건수는 정책별로 2~4건이었다. 어느 정책도 모든 결함을 확정하지 못했고, 모터 F2 두 건은 다섯 정책 모두 검사 예산 안에서 HOLD였다.

이 평가는 알려진 결함 유형에 새 seed를 적용한 비교다. 새 seed를 새로운 결함 유형으로 세지 않는다. 결과는 등록된 네 결함 유형과 두 정상 원천에서의 관측이며, 처음 보는 결함에 대한 일반화나 특정 방식의 전반적 우위를 뜻하지 않는다.

## 평가 질문

같은 원천과 검사 도구를 제공했을 때 다음 다섯 정책이 어떤 검사를 고르고, 세 번의 짝 검사 예산 안에서 올바른 원인군을 확정하는지 비교했다.

| 정책 | 검사 선택 방식 | 모델 호출 |
|---|---|---:|
| `fixed_eligible` | 등록된 고정 순서 | 0 |
| `logs_only` | 학습 수치를 받은 모델이 다음 검사 선택 | 18 |
| `logs_plus_frames` | 같은 수치와 같은 Play 프레임을 받은 모델이 다음 검사 선택 | 12 |
| `optimizer_first_registered_rule` | 옵티마이저 검사부터 시작하는 등록 규칙 | 0 |
| `registry_next` | 검사 registry의 다음 후보 사용 | 0 |

두 모델 정책의 요청 모델 ID는 `nvidia/nemotron-3.5-super-vl-120b-a12b`다. 모델은 등록된 검사 ID와 근거 ID를 고른다. 검사 인자와 기대값은 호스트가 만들고, 검사 실행·원인 확정·교정 가능 여부도 호스트가 판정한다. 모델 출력만으로 원인을 확정하거나 실행 권한을 만들지 않는다.

## 사례와 분모

| 사례 | 유형 | 건수 | 평가상 위치 |
|---|---|---:|---|
| case-01·02 | 정상 NONE | 2 | 정상 gate와 모델 shadow 기록 |
| case-03·04 | 보상 F1 | 2 | 등록 교정 범위 안 |
| case-05·06 | 모터 F2 | 2 | 등록 교정 범위 안 |
| case-07·08 | 보상·갱신 복합 F1+R1 | 2 | 부분 확정과 전체 확정 분리 |
| case-09·10 | 마찰 F5 | 2 | 진단 대상, 교정 범위 밖 |

10개 사례 체크포인트는 서로 다른 독립 원천이다. 결함 8건과 정상 2건이며, 알려진 결함 유형은 F1·F2·F1+R1·F5 네 가지다. 같은 사례를 다섯 정책으로 반복한 행, 모델 재호출, 프레임 수는 독립 사례 수를 늘리지 않는다.

모든 정책은 같은 기본 학습 사실, 같은 등록 검사 도구, arm당 최대 짝 검사 3회를 사용했다. `logs_plus_frames`에만 같은 Play 프레임이 더해졌다. 정책 실행 순서는 사례마다 회전했고, 계획된 10사례 × 5정책을 완료·HOLD·기술 중단 가운데 하나로 봉인했다.

## 판정 기준

주지표는 결함 사례에서 예산 안에 기대 원인군을 올바르게 확정했는지다. 잘못된 확정은 별도로 세고, 검사 결과가 모두 normal이거나 예산이 끝나면 HOLD로 남긴다.

복합 결함은 두 층으로 나눴다.

- `compound_partial`: F1 또는 R1 가운데 한 원인군만 올바르게 확정했다.
- `compound_full`: 두 원인군을 모두 확정했다.

정상 사례에는 두 경계가 있다. 먼저 private benchmark host gate가 실행을 막는다. 모델 정책에는 실행 권한이 없는 shadow 판단을 한 번 기록한다. host gate가 막았다는 사실을 모델이 정상을 식별한 것으로 세지 않는다.

F5는 물리 원인군을 확정할 수 있어도 등록 교정이 없으므로 `repair_unsupported`로 HOLD해야 한다. 진단 확정과 교정 지원 여부를 같은 성공으로 합치지 않는다.

## 정책별 실제 결과

| 정책 | 올바른 원인군 확정 | HOLD | 복합 부분 / 전체 | 짝 검사 합 | API 호출 |
|---|---:|---:|---:|---:|---:|
| `fixed_eligible` | 3/8 | 7/10 | 2 / 0 | 22 | 0 |
| `logs_only` | 4/8 | 6/10 | 2 / 0 | 16 | 18 |
| `logs_plus_frames` | 4/8 | 6/10 | 2 / 0 | 10 | 12 |
| `optimizer_first_registered_rule` | 4/8 | 6/10 | 2 / 0 | 18 | 0 |
| `registry_next` | 2/8 | 10/10 | 0 / 0 | 22 | 0 |

잘못된 원인 확정은 다섯 정책 모두 0건이었다. `fixed_eligible`의 10행에는 기술 중단 1행이 포함돼 있으며, 이 행은 원래 상태를 보존했다. 표의 확정 건수만으로 정책 간 우위를 선언하지 않는다.

복합 사례 두 건에서 `fixed_eligible`, 두 모델 정책, optimizer-first 규칙은 각각 부분 원인만 2건 확정했다. 전체 원인 확정은 모든 정책에서 0건이었다. 따라서 `2/2`는 복합 결함 해결이나 전체 진단 성공이 아니다.

이 진단 단계는 첫 원인군이 확정되면 종결한다. [실행기](../evals/lineage_five_policy_driver_v1.py)의 `full_cause_confirmation`은 복합 사례에서 `false`이므로, 집계된 전체 확정 0은 모든 원인을 찾아내는 능력을 측정한 실패율이 아니다. 교정 뒤 남은 실패와 두 번째 진단은 별도 R4 고리에서 평가한다.

## 사전등록한 주 비교

주 비교는 `logs_only`와 `fixed_eligible`의 짝 비교다. 기술적으로 비교 가능한 결함 쌍은 7건이고, 1건은 기술 중단으로 빠졌다.

| 항목 | `logs_only` | `fixed_eligible` |
|---|---:|---:|
| 비교 가능한 7건의 올바른 확정 | 3 | 3 |
| 두 정책이 함께 맞힌 사례 | 3 | 3 |
| 함께 맞힌 사례의 짝 검사 합 | 3 | 9 |

두 정책 중 한쪽만 맞힌 불일치 쌍은 0건이었다. 양측 exact sign test는 `p=1.0`, 등록 판정은 `inconclusive`다. 함께 맞힌 세 사례에서는 수치 모델 정책이 검사 3회, 고정 순서가 9회를 사용했지만, 이 조건부 차이를 전체 정책의 시간·비용 우위로 확대하지 않는다.

정책 전체 집계에서는 `logs_only`가 4/8, `fixed_eligible`가 3/8이다. 주 비교가 3대3인 이유는 기술 중단이 있는 같은 짝만 제외했기 때문이다. 서로 다른 분모의 숫자를 한 효과값처럼 합치지 않는다.

## 프레임 추가 비교

`logs_plus_frames`와 `logs_only`는 결함 원인군을 각각 4/8 확정했다. F5 두 사례에는 같은 Play 프레임이 없어 기술 비교 가능한 짝은 6건이다. 여섯 짝에서 한쪽만 맞힌 사례는 없었고 exact sign test는 `p=1.0`, 판정은 `inconclusive`다.

두 정책이 함께 맞힌 네 사례의 검사 합도 각각 4회였다. 프레임 정책의 원시 frame fact 인용은 0건이다. 이번 실행에서는 프레임 추가가 더 유용한 검사를 고르게 했거나 원인 확정 수를 높였다는 근거가 나오지 않았다.

프레임이 있는 여섯 결함 쌍에서 요청·응답·검사 연결은 유효했다. 확인한 것은 프레임을 포함한 요청과 후속 검사 연결이다. 픽셀 정보가 검사 선택에 기여했는지는 확인되지 않았다.

## 정상 사례의 shadow 판단

두 모델 정책은 정상 사례 두 건에서 각각 2/2 shadow 검사 제안을 남겼다. 합계 4/4 제안이다. 이 제안은 실행되지 않았고, 정상 host gate가 개입을 차단했다.

따라서 이 네 건은 모델의 정상 식별 성공이 아니다. 오히려 모델 제안과 실행 안전 경계를 분리해야 한다는 관측이다. 규칙 정책 세 개는 정상 행에서 모델을 호출하지 않았다.

## 유형별로 드러난 공백

### 모터 F2

case-05·06은 다섯 정책 모두 세 번의 검사 예산을 소진한 뒤 HOLD였다. 어느 정책도 `P_torque`를 선택하지 않았다. 선택된 검사는 보상, 에피소드, 노이즈, 값 함수, 물리, 옵티마이저 갱신 범주 안에 머물렀고 결과는 모두 normal이었다.

이 결과만으로 `P_torque` 검사 자체가 F2를 잡지 못한다고 결론낼 수 없다. 원래 50행이 보여주는 사실은 검사 선택 경로가 두 F2 사례에서 해당 검사를 고르지 못했다는 점이다.

별도 사후 개발 대조에서는 같은 두 체크포인트와 정상 참조에 `P_torque`를 적용했고, 두 사례 모두 `abnormal / confirmed_signature`였다. 새 짝 검사 2회·SDK 역할 4회를 예약했으며 모델 호출·교정·학습은 없었다. 이 대조는 정답 유형 F2를 알고 검사를 고른 oracle이므로 원래 선택기 성과에 더하지 않는다. 이 두 조건에서는 등록 검사가 이상을 관측할 수 있었지만 선택 경로가 해당 검사를 고르지 못했다. 검사 도구의 관측 능력과 다음 검사 선택의 공백을 분리한 결과다.

### 교정 범위 밖 F5

case-09·10에서 `registry_next`는 `P_value` normal 뒤 `P_physics` abnormal을 얻어 두 사례 모두 physics 원인군을 확정했다. 이어서 등록 교정이 없어 `repair_unsupported` HOLD로 끝났다.

수치 모델과 고정 순서, optimizer-first 규칙은 F5 수치 입력에서 physics 원인군을 확정하지 못했다. 프레임 정책은 두 사례 모두 프레임 부재로 HOLD였다. 진단 가능성과 교정 지원을 분리했기 때문에 `registry_next`의 2건도 회복 성공으로 세지 않는다.

## 실행량과 시간 해석

완료 batch는 짝 검사 intent 89건, SDK 역할 예약 178건 가운데 실행 177건을 기록했다. 원래 중단 전 완료 18행을 재사용했고, 부분 행 1건을 봉인했으며, 미시작 31행을 이어서 실행했다. 모델 요청은 이전 7건과 새 23건, 합계 30건이다. 자동 재시도는 0건이다.

부분 행에는 정상 참조 역할 1건의 영수증이 남았고, 짝의 나머지 역할 1건은 실행되지 않았다. 이 둘을 모두 0회 실행으로 바꾸지 않는다.

batch 부모 wall 합은 `26423.893268999982`초다. 이전 구간과 재개 구간의 scope가 섞여 있고, 중단 행의 시간은 하한이므로 정책별 벽시계 비교나 GPU 절감 계산에 쓰지 않는다.

정책 집계의 `owned_child_wall_s=0`은 SDK 실행 시간이 0초라는 뜻이 아니다. 완료 probe의 자식 시간이 원문 집계에서 unknown으로 남았기 때문에 known 합이 0인 상태다. [별도 비용 감사](LINEAGE-PROBE-COST-AUDIT.md)는 실행한 역할 177건의 시간을 모두 확인했고, 한 번만 합산한 orphan 역할을 포함해 owned wall `4,161.601초`를 복원했다. 명시적 미실행은 1역할, 미확인·미해소 예약은 0건이다. [공개 감사 결과](../evals/results/lineage_probe_cost_audit_20261102_v1/)는 원문과 다른 계측 범위를 표시하며, 이 시간을 GPU 커널 시간이나 정책 간 절감률로 바꾸지 않는다.

## 이 결과가 말하는 범위

이번 비교에서 확인된 것은 같은 10개 원천과 검사 예산에서 정책에 따라 선택 경로와 종결 상태가 달라졌다는 점이다. 모델 정책과 optimizer-first 규칙은 각각 4/8 원인군을 확정했고, registry 정책은 교정 범위 밖 F5를 두 건 확정했다. 어느 한 방식도 F2를 찾거나 복합 결함의 두 원인을 모두 확정하지 못했다.

이 수치로 LLM의 전반적 우위, 모델 버전 향상, 영상의 진단 이득, GPU 비용 절감, 처음 보는 결함에 대한 일반화를 주장하지 않는다. 평가 대상은 알려진 네 결함 유형의 새 seed이며, 교정과 재학습 뒤 회복은 R3 진단 비교에 포함되지 않는다.

사후 F2 oracle 대조의 2/2 이상 관측은 별도 개발 대조이며 원래 비교의 성공률을 바꾸지 않는다. R4 종단 회복은 별도 단계에서 진행 중이며, 새 회복 성과를 진단 비교 결과에서 추정하지 않는다.
