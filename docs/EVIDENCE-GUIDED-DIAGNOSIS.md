# 관측 근거를 읽고 검사를 고르는 고리

호스트가 만든 행동 ID를 선택하는 계약을 연결한 뒤, 같은 학습 자료의 개발 비교에서 모델의 첫 응답12/12가 유효했다. 근거 조회 방식은 처음6건 모두 HOLD였지만, 검사별 등록 예측을 설명한 후속 판에서는 보상 결함1건과 복합 결함의 보상 원인1건을 검사로 확인했다. 나머지4건은 HOLD였다. 앞선 계약의 실패와 보강 뒤 결과를 함께 보존한다.

## 같은 자료와 도구에서 비교한 방법

[source 등록](../bench/protocols/prospective_diagnosis_training_20261101_v1.json)은 seed2320·2321 각각에서 NONE, 보상 좌표계 결함 F1, PPO epoch 결함 R1_ONLY, 두 결함의 복합 조건을 학습하도록 고정했다. 모두 환경4096개에서300 update를 학습하고26조건 고정 평가를 받았다. 알려진 등록 결함군의 새 학습 seed이며 새로운 결함군 평가는 아니다.

정상 정책의 수평 속도 오차는0.1408~0.1451m/s, 결함6조건은1.1684~1.1958m/s였다. 모든 정책의 평균 생존은20초, 낙상률은0이었다. 이 source 확인은 학습·평가 완료이며 진단 성공이나 교정 회복으로 세지 않는다.

[진단 비교 v5](../bench/protocols/prospective_agentic_comparison_20261101_v5.json)는 모델 호출 전에 세 방식을 고정했다.

| 방식 | 처음 받는 자료 | 이후 행동 |
|---|---|---|
|eager model|텔레메트리와 검증된 optimizer 횟수|모델이 등록 검사를 선택|
|evidence-guided model|텔레메트리와 조회 가능한 횟수 자료 목록|모델이 근거 조회 또는 검사를 선택|
|등록 규칙|같은 횟수 자료를 조회|case가 불일치하고 참조가 정상이면 count 검사, 나머지는 기존 등록 순서|

두 모델 방식의 정보원·검사 목록·인자·판정 기준은 같다. 횟수 자료의 노출 시점이 다르다. 모델은 행동·대상·fact ID를 선택하고, 호스트가 실행 인자·승인·교정을 담당한다. 등록 규칙은 횟수 이상을 우선하는 기준선이며 모든 가능한 규칙의 최적해는 아니다.

각 진단은 paired 검사3회, 모델 행동4회, 행동당 형식·의미 피드백1회로 제한했다. 정상2조건은 호스트 고정 평가 관문에서 각 방식의 모델 호출과 검사를0회로 막았다. 이6행은 모델의 정상 판별 성공이 아니다. 전체는8조건×3방식=24행이며 정상 관문6행과 결함 진단18행을 분리한다.

## 실제 결과

[공개 결과](../evals/results/prospective_agentic_comparison_20261101_v2/summary.json)는 계획24행을 모두 보존한다. 전체 모델 요청은32회, paired 검사는10회였다. 교정과 회복 학습은 이 비교에 포함하지 않았다.

| 방식 | 결함 진단 수 | 단일 결함 확정 | 복합에서 한 원인군 확정 | 결함 진단 HOLD | paired 검사 | 모델 요청 |
|---|---:|---:|---:|---:|---:|---:|
|eager model|6|0|0|6|0|12|
|evidence-guided model|6|0|0|6|0|20|
|등록 규칙|6|2|2|2|10|0|

복합의 부분 확정은 두 원인 전체를 알아낸 성공이 아니다. 두 seed의 R1_ONLY에서 규칙이 optimizer update-count를 확정했고, 복합에서는 같은 원인군 하나를 확인했다. F1 두 조건은 검사 예산 안에서 원인을 확정하지 못했다.

| 모델 행동의 유효성 | 첫 응답 | 피드백 후 |
|---|---:|---:|
|eager model|0/6행동|0/6행동|
|evidence-guided model|0/10행동|4/10행동|

근거 조회 방식의 유효 행동4개는 자료를 읽는 행동이었다. 이후 검사 선택은 무효여서 실제 검사를 실행하지 못했다. 유효 행동 비율은 원인 진단 정확도가 아니다.

실제 응답은 `action` 칸에 `P_recorded_optimizer_updates` 같은 검사명을 넣었다. 허용된 행동은 `read_evidence`, `run_probe`, `hold`이므로 `F_ACTION`이었다. 피드백 뒤에도 같은 종류의 오류가 남았다. 현재 프롬프트의 enum·완전한 응답 예시 안내가 약했다는 것은 코드에서 세운 가설이며, 모델의 RL 분석 능력 전체를 이 결과로 평가하지 않는다. 원문을 의도에 맞춰 사후 변환하지 않았다.

두 seed 안의 여러 결함 조건은 서로 완전히 독립된 표본이 아니다. 사례별 결과와 계획 분모를 보고하며, 이 작은 묶음에서 모집단의 효과나 규칙 대비 우위를 추정하지 않는다.

## 새 행동 ID 계약

새 [option 계약](../evals/registry_action_options_v1.py)은 모델이 현재 `action_options`의 `option_id`와 읽을 수 있는 `fact_ids`만 반환하게 한다. 호스트가 action과 target을 조합한다. JSON schema, 정확한 fact ID 목록과 count의 expected/min/max 묶음을 프롬프트에 제공하며, 피드백에도 같은 허용값을 보낸다. 이는 프롬프트와 클라이언트 검증이며 provider의 constrained decoding을 사용한 결과는 아니다.

[새 고리](../evals/registry_action_loop_v1.py)는 이 선택을 기존 request spec·승인·역할별 영수증 검증에 연결한다. 검사 관측 뒤에는 상태와 후보를 갱신해 다음 행동을 고른다. 무효 응답은 피드백1회 뒤 HOLD, 자료 조회와 HOLD는 검사 실행0회다. 호스트가 모델의 근거 ID나 검사 결과를 대신 만들지 않는다.

[BFCL(ICML2025)](https://proceedings.mlr.press/v267/patil25a.html)의 도구 호출 형식·인자 오류 분리와 [ToolSandbox](https://arxiv.org/abs/2408.04682)의 상태별 관측·단계 평가를 참고했다. 해당 벤치마크의 코드나 점수를 이식하지 않았다. 이 고리에서는 형식 유효성, 실제 원인 확정, 승인된 수리, 독립 고정 평가 회복을 각각 확인한다.

[후속 사전등록](../bench/protocols/registry_action_contract_development_20261101_v1.json)은 같은 source에서 새 계약을 확인하는 개발 측정이다. 기존 무효 응답은 그대로 두고 새 요청과 실행을 분리했다. 요청 모델과 파라미터, 원 학습 자료와 검사 예산을 유지하고 행동 ID·허용 선택지·피드백 계약을 바꿨다. 전체 메시지가 같은 비교는 아니며, 이미 본 입력의 결과를 새 seed 성능이나 모델 버전 효과로 부르지 않는다.

## 새 계약의 개발 측정

[공개 결과](../evals/results/registry_action_contract_development_20261101_v1/summary.json)는 계획16행을 모두 보존한다. 정상 host gate4행을 제외한12개 첫 결정이 재요청 없이 유효했다. 이전 판의 같은 첫 결정은0/12였다. 아래 첫 유효는 원인 정확도가 아니라 계약 통과 여부다.

| 새 계약 방식 | 첫 결정 유효 | 단일 결함 확정 | 복합에서 한 원인군 확정 | 결함 진단 HOLD | paired 검사 | 모델 요청 |
|---|---:|---:|---:|---:|---:|---:|
|근거 즉시 제공|6/6|2|2|2|6|8|
|모델이 근거 조회 선택|6/6|0|0|6|0|6|

원인을 확인한4행은 eager 방식의 R1_ONLY와 복합 조건이었다. 모델이 `P_recorded_optimizer_updates`를 골랐고, 새 승인·일회 소비 영수증이 case의 기대20/관측4와 참조20/20을 확인했다. 두 복합 행은 optimizer 원인군만 확인한 부분 진단이다. 검사는6회 모두 보관된 계측의 CPU 재검증이었고 새 SDK 실행은0회였다.

F1 두 행은 정상 count 검사 뒤 HOLD였다. 근거 조회 방식은 첫 행동으로6행 모두 유효한 HOLD를 선택했다. 형식 유효율이 높아져도 조사나 진단이 나아진 것은 아닐 수 있음을 이 결과에서 확인했다. 새 계약은 사전등록한 형식 후보 조건을 통과했지만 기본 모드로 채택하지 않았다. 등록 규칙 대비 진단 우위도 확인하지 못했다.

검사에서 확정된 c03/eager 사례 하나의 후속 회복 대상을 모델 결과 전에 [별도 등록](../bench/protocols/registry_action_recovery_s3332_20261101_v2.json)했다. 교정은 호스트 규칙 `restore_configured_ppo_epochs`, 회복 방식은 독립 seed3332의300-update 새 학습이다. 모델은 검사만 선택하며 교정 인자와 회복 판정 권한은 갖지 않는다. 이 진단 비교의14회 모델 요청과 후속 회복의 추가 모델 요청0회를 분리한다.

## 선택한 검사에서 교정과 회복까지

사전 고정한 한 사례는 [고정 평가에서 recovered](../evals/results/registry_action_recovery_s3332_20261101_v1/summary.json)였다. 새 옵션 원문·source·승인·count 영수증을 재검증한 뒤 PPO epoch를 등록값5로 복원했다. 학습 첫 세 update는 기대20회 대비 관측20회였다. 원 결함 checkpoint의 가중치는 불러오지 않고 seed3332에서300 update를 새로 학습했다.

| 정책 | 학습 seed | 수평 속도 RMSE(m/s) | 회전 속도 RMSE(rad/s) | 평균 생존(s) | 낙상률 |
|---|---:|---:|---:|---:|---:|
|R1 결함|2320|1.1813|0.7808|20.00|0%|
|epoch 복원 후 새 학습|3332|0.1520|0.2697|19.28|3.85%|
|정상 참조 NONE|2320|0.1451|0.2981|20.00|0%|

교정 정책은 수평 추종·회전 추종·생존·낙상의 등록 기준 네 개를 통과했다. 낙상은26조건 중1건이었으며 무낙상 결과는 아니다. 정상 참조는 기존 정책을 평가 기준으로 재사용했고 새 회복으로 세지 않았다.

이 후속 실행은 smoke·새 학습·고정 평가의 SDK3회와 추가 모델 호출0회로 마쳤다. 부모 실행 구간은651.906초였으며 CUDA 커널 시간이 아니다. 모델은 확인 검사를, 등록 규칙은 교정과 fresh restart를 선택했다. 진단 입력은 이미 본 자료이고 회복 대상도 한 사례이므로 새로운 결함군 대응·모델 버전 효과·일반적 회복률의 근거로 넓히지 않는다.

## 보관된 횟수 자료의 검사 비용

별도 [recorded 검사 audit](OPTIMIZER-OBSERVABILITY.md#보관된-학습-계측을-재사용하는-검사)에서는 두 seed 모두 새3-update 검사와 같은 count·판정을 얻었다. 부모 시간은 약203~205초에서40초였고 추가 SDK 실행은 각2회에서0회였다. 이는 보관된 첫3-update 계측이 있는 조건의 도구 효과다. 모델 선택 효과·CUDA 커널 시간·조기 탐지·학습 절감·회복은 이 audit의 측정 대상이 아니다.

## 검사별로 가를 수 있는 후보를 설명한 후속 판

형식이 유효해도 조회 방식6건이 모두 멈춘 점을 다음 구현 대상으로 삼았다. [Active diagnosis 연구](https://proceedings.mlr.press/r15/pu17a.html)는 이전 관측에 따라 다음 관측을 선택하는 문제를 다룬다. [MediQ](https://proceedings.neurips.cc/paper_files/paper/2024/hash/32b80425554e081204e5988ab1c97e9a-Abstract-Conference.html)는 정보가 부족할 때 추가 질문과 최종 판단을 구분하되, 질문을 권하는 프롬프트만으로는 성능이 나빠질 수 있음을 보고했다. 이 프로젝트에서는 추가 조회 행동이 이미 있으므로 행동 종류를 늘리거나 조회를 강제하지 않았다.

새 [option v2](../evals/registry_action_options_v2.py)는 각 검사의 등록 예측을 `normal`, `abnormal`, `unspecified` 후보 목록으로 보여 준다. 이는 실제 관측이나 정답이 아니다. `unspecified` 후보는 정상·이상 결과 어느 쪽에서도 제거하지 않는다. 등록 비용은 실행 시간의 측정값이 아니며, 확률·정보 이득 점수·추천 순위를 만들지 않는다. 증상만으로 원인을 확정하는 일과, 아직 모르는 검사 결과로 후보를 가르는 일을 설명하고 HOLD는 계속 허용한다.

[사전등록](../bench/protocols/diagnostic_option_study_20261101_v1.json)과 [공개 결과](../evals/results/diagnostic_option_study_development_20261101_v2/summary.json)는 같은 학습 자료8개에서 조회 방식 하나를 확인한 개발 측정이다. 모델·요청 파라미터·관측 자료·검사와 예산은 유지했다. 등록 예측 메타데이터를 새로 노출하고 설명·예시를 바꿨으므로 전체 입력이 같은 비교는 아니다. 출력은 여전히 `option_id`, `fact_ids`뿐이며 기존 승인·영수증·원인 확정 조건을 유지한다.

| 조회 방식 | 결함 첫 결정 유효 | 단일 결함 확정 | 복합의 한 원인군 확정 | 결함 HOLD | paired 검사 | 모델 요청 |
|---|---:|---:|---:|---:|---:|---:|
|행동 ID 계약 v1|6/6|0|0|6|0|6|
|등록 예측 설명 v2|6/6|1|1|4|3|7|

- seed2321 F1에서 모델은 추종 보상 fact 네 개를 인용해 `P_reward`를 골랐다. 승인된 paired 검사가 보상 원인군을 확인했다.
- 같은 seed의 복합 조건에서도 `P_reward`가 보상 원인을 확인했다. optimizer 결함까지 확인한 전체 진단은 아니다.
