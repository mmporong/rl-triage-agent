# 검사 선택 입력의 개발 측정

Nemotron 3.5 Super VL 요청 경로에서 고정한 과거 입력 여섯 건을 호출했다. 두 사례의 첫 epoch와 첫 검사 기록을 이미 본 뒤 만든 개발 측정이다. 이 실행은 모델 호출 계약과 입력 노출에 따른 선택 변화만 확인했으며, 새 학습·GPU 실행·검사는 수행하지 않았다.

## 실행 결과

최종 응답은 6/6건이 계약에 맞았다. HTTP 요청은 7회였고, 6회 성공과 500 오류 1회가 기록됐다. 오류 뒤 등록된 인프라 재시도 1회에서 유효 응답을 받았다. 대기 중인 요청과 시간 초과는 없었다.

사전등록한 엄격한 기준은 모든 HTTP 요청의 성공을 요구한다. 따라서 실행 상태는 `complete`지만 `runtime_verified=false`다. production 입력의 첫 시도 유효율 1/2는 모델 출력 형식 위반이 아니라 HTTP 500 오류에서 비롯됐다.

| 사례 | production 선택 | 전체 관찰 입력 | 마스킹 관찰 입력 | 선택 변화 |
|---|---|---|---|---|
| case 1 | `P_episode` | `HOLD` | `HOLD` | 없음 |
| case 2 | `P_episode` | `P_reward` | `P_reward` | 없음 |

두 노출 쌍 모두 최신 관찰 사실을 인용했지만, 전체 관찰과 마스킹 관찰에서 선택은 같았다. 이 결과는 최신 사실의 인용 여부를 보여줄 뿐 선택에 미친 인과 효과나 회복 성능을 입증하지 않는다. 보조 노출 입력은 실행 결정에 쓰지 않았다.

## 사용량과 결합

성공 응답 6회의 기록된 토큰은 입력 16,676개, 출력 319개, 합계 16,995개다. 실패 응답에는 사용량이 없어 전체 요청의 토큰 합계는 계산하지 않았다. 일곱 요청의 벽시계 시간 합계는 106.48190629208693초다.

[공개 요약](../evals/results/selection_runtime_v2_20261023/summary.json)은 실행 경계와 사용량을, [선택 기록](../evals/results/selection_runtime_v2_20261023/decisions.json)은 여섯 조건의 최종 선택을 담는다. [재현 결합](../evals/results/selection_runtime_v2_20261023/provenance.json)은 실험 커밋과 두 프로토콜, 원본 capsule 6개, 호출 기록 6개, HTTP 원장 7개의 해시를 보존한다. 공개 파일에는 사용자 경로, 비공개 경로, 계정 정보, 원시 프롬프트와 응답, API 키를 넣지 않았다.

이 측정은 selector 정책 네 가지의 종단 비교가 아니다. D3와 D4의 구현·성능 결과로 합산하지 않는다.

## 새 seed에서 검사 선택 정책 비교

[실행 계약](../bench/protocols/selection_comparison_demo_v1.json)은 seed 2170의 보상·PPO epoch 복합 결함 하나에 네 정책을 적용한다. 정상 대조, 결함 원본, 초기 고정 평가와 정상 참조 검사만 공유한다. 이후 검사 원장, 교정 학습, 후속 평가와 체크포인트 계보는 정책마다 분리한다. 네 정책의 결과를 독립 사례 네 개로 세지 않는다.

| 정책 | 다음 검사 선택 |
|---|---|
| `registry_next` | 현재 후보와 관측에 맞는 등록 순서 |
| `fixed_eligible` | 고정 목록에서 현재 실행 가능한 첫 검사 |
| `model_first_then_rule` | 각 진단 단계의 첫 선택은 모델, 유효한 첫 선택 이후에는 등록 순서 |
| `model_adaptive` | 새 검사 관측마다 같은 공개 정보뷰를 모델에 제공 |

모델은 검사 ID와 근거 사실 ID를 고른다. 검사 인자·예상 결과·등록 교정과 회복 판정은 호스트가 만든다. 모델 응답이 고정 피드백 한 번 뒤에도 무효이거나 호출 근거가 확인되지 않으면 해당 정책은 `HOLD`로 멈춘다. 무효 응답을 규칙 선택으로 바꾸지 않는다.

검사와 교정 실행 전에는 각각 사용자 위임 운영자 승인을 봉인한다. 두 번째 진단 단계는 같은 정책의 첫 교정이 고정 평가에서 `not_recovered`였다는 검증된 기록이 있을 때만 열린다. 서로 다른 등록 교정은 최대 두 개이며, 각 교정 학습은 누적 교정을 적용한 새 초기화에서 시작한다. 모델이 교정 방법을 고르는 경로는 이번 비교에 포함하지 않는다.

실행 상한은 모델 HTTP 요청 60회, 300회 갱신 학습 10개, 고정 평가 단계 9개다. 논리 대화 20개에는 각각 최초 요청과 고정 피드백·인프라 재시도 각 한 번을 합쳐 최대 세 요청을 배정한다. 소유 자식 프로세스의 부모 벽시계 합은 16,200초, controller 예산 시작 후 경과 시간은 18,000초로 제한한다. 이는 예상 소요 시간이나 GPU 커널 시간 측정값이 아니다. 전체 관찰·마스킹 관찰의 보조 호출은 각 진단 단계의 첫 유효 검사 뒤에만 수행하며 실행 결정에 쓰지 않는다.

설계에는 이미 확인한 두 교정 회복 기록과 위 여섯 모델 대화가 반영됐다. 최종 계약을 고정하기 전에 PPO 계산 결함 seed 2165의 모델 계약 위반도 확인했다. 새 비교 결과는 이 개발 과정과 분리해 기록한다.

실행기는 다음 명령으로 커밋·소스·새 seed·GPU 입장 조건을 확인한 뒤 공용 임대 안에서 실행했다. seed 2170과 해당 실행 태그는 소비됐으며 같은 명령으로 다시 실행하지 않는다.

```powershell
cd (Join-Path $HOME 'rl-triage-agent')
.\bench\run_selection_comparison_demo_v1.ps1 -Execute
```

## seed 2170의 부분 실행 결과

선택 정책 비교는 `invalid`로 끝났다. 첫 정책 `model_first_then_rule`의 두 번째 진단 단계에서 실행 이름이 등록된 길이 제한을 넘어 다음 검사를 시작하지 못했다. 네 정책의 비교 결과는 아직 없다.

정상과 복합 결함 정책을 각각 300회 학습한 뒤 고정 평가로 결함의 행동 실패를 확인했다. 첫 모델 응답은 유효했고 `P_reward`를 선택했다. 검사 결과는 `abnormal`이었으며, 보상 좌표계를 복원한 재학습 300회 뒤에도 추종은 회복되지 않았다.

검증된 `not_recovered` 기록에 따라 두 번째 진단 단계가 열렸다. 모델은 유효한 응답으로 `P_episode`를 선택했고, 이후 등록 순서에 따른 `P_value`, `P_physics`, `P_noise`까지 네 검사가 모두 `normal`이었다. 다음 `P_optimizer_updates`의 실행 계획 검증에서 83자 이름이 80자 제한에 걸렸다. 저장된 상태로 이 경계를 CPU에서 재현했으며, 같은 계획에 77자 이름을 쓰면 검증이 통과했다. 모델 출력 계약 위반으로 분류하지 않는다.

완료된 모델 요청 두 건은 모두 첫 응답이 유효했고 피드백이나 인프라 재시도를 쓰지 않았다. API는 상한 60회 중 2회, 기록된 토큰은 5,447개였다. 대기 중인 API·검사·교정 요청은 없었다. 소유 자식 프로세스의 부모 벽시계 합은 1,939.439초이며 GPU 커널 시간이나 완료된 네 정책의 비용을 뜻하지 않는다. 두 번째 교정과 나머지 세 정책은 실행하지 않았다.
