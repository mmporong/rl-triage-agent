# 교정 뒤 남은 결함을 다시 진단한 결과

F1 보상 결함과 R1 PPO epoch 결함을 함께 넣은 실행에서, 첫 교정 뒤 남은 실패를 두 번째 진단으로 넘기는 고리를 확인했다. 새 선택 계약을 쓴 v2는 seed 2120·2121 모두 서로 다른 교정 두 건을 거쳐 고정 평가를 통과했다. 첫 판의 seed 2110·2111은 두 번째 모델 응답이 출력 계약을 통과하지 못해 `HOLD`로 끝났으며 그 기록도 보존했다. [v2 공개 요약](../evals/results/residual_success_public_20261017/summary.json) · [v1 공개 요약](../evals/results/residual_failure_public_20261017_v2/summary.json)

이 측정은 앞선 F1·R1 단일 결함과 수리 결과를 본 뒤 설계했다. 새 seed를 썼지만 이 설계 결합은 남아 있으며, 복합 결함 전반의 결과로 해석하지 않는다.

## v1: 두 seed에서 같은 지점까지 진행

| seed | 정상 NONE 수평 RMSE | 복합 결함 수평 RMSE | 첫 교정 뒤 수평 RMSE | 첫 교정 판정 | 최종 상태 |
|---:|---:|---:|---:|---|---|
| 2110 | 0.1481 m/s | 1.1793 m/s | 1.1898 m/s | `not_recovered` | `HOLD` |
| 2111 | 0.1518 m/s | 1.1720 m/s | 1.1732 m/s | `not_recovered` | `HOLD` |

두 seed의 정책은 20초 평가를 유지했고 낙상률은 0이었다. 생존 지표만 보면 차이가 작지만, 복합 결함과 첫 교정 정책은 명령 추종 오차가 정상 기준으로 돌아오지 않았다. 첫 교정의 유효한 `not_recovered` receipt를 검증한 뒤에만 두 번째 epoch를 열었으므로, 처음부터 진단에 실패한 실행은 아니다. 여섯 평가 원본은 [공개 결과 폴더](../evals/results/residual_failure_public_20261017_v2/evaluations/)에 있다.

## 멈춘 원인

모델 대화는 두 seed를 합쳐 6건이었고, API 호출은 등록 상한 20회 중 10회를 썼다. 첫 epoch의 진단 두 건은 첫 응답에서 내부 하위 유형 7개를 공개 범주 6개 자리에 넣어 `D_RANKING`을 받았다. 한 번의 피드백 뒤에는 공개 범주 6개와 상위 3개 기대값을 맞춰 유효해졌다. 교정 제안 두 건도 첫 응답에서 유효했다.

두 번째 epoch에서는 같은 형식 오류가 반복됐다. 첫 응답은 7개 하위 유형을 순위에 넣어 `D_RANKING`이었고, 피드백 뒤 순위는 고쳤지만 `expected_outcomes`에 상위 3개가 아닌 6개 범주를 넣어 `D_EXPECTED`가 됐다. 대화 6건 중 4건은 최종 유효, 2건은 최종 무효였다. 원응답 10건을 따로 세면 유효 4건, 무효 6건이다.

[계약 감사 결과](../evals/results/residual_failure_public_20261017_v2/model_contract_audit.json)는 전달 프롬프트와 검증기가 같은 규칙을 요구했음을 확인한다. 순위는 공개 범주 6개의 순열이어야 하고, `continue` 응답의 기대값은 선택한 probe에 대해 순위 상위 3개만 담아야 한다. 같은 packet으로 이 형식을 만족하는 응답을 만들 수 있으므로, 이번 중단은 실행기의 계약 불일치가 아니라 모델 응답의 계약 위반으로 분류했다. V1 기록은 그대로 보존하며 같은 의미의 재시도는 하지 않는다.

## 남은 경계 문제

[사실] 두 번째 진단은 보상 교정이 적용된 상태에서도 `reward`를 1위로 놓고 `P_reward`를 다시 골랐다. 형식 검증이 먼저 실패해 probe는 실행되지 않았다.

[사실] 등록표에서 `P_reward`의 나머지 가설 기대값은 모두 `normal`이어서, 보상 가설을 제외한 뒤에는 후보를 나누지 못한다. CPU 재현에서는 기대값을 상위 3개로만 줄인 응답이 기존 검증을 통과했고, `P_reward` 선택도 그대로 남았다. 이 사후 재현은 원래 모델 응답의 무효 판정을 바꾸지 않는다.

[추론] 이 경계 문제는 이번 `D_EXPECTED`의 원인은 아니지만, 출력 형식과 함께 다음 검사가 남은 후보를 구분하는지도 확인해야 한다는 근거가 된다.

## v2: 두 번째 검사와 교정 뒤 회복

v2에서는 모델이 `action`, `probe`, `fact_ids`만 선택하고, 기대값·사실의 수치·실행 인자는 호스트가 만든다. 형식 검사와 의미 검사를 분리해, 고른 검사가 현재 가설을 구분하는지 확인한다. 후보가 하나면 해당 후보의 등록 abnormal 확정 검사를 허용한다. 유효한 모델 선택은 그대로 쓰며, 피드백 뒤에도 형식·의미가 무효이면 등록 규칙으로 검사 선택을 넘기고 선택 주체를 기록한다.

교정은 새 abnormal 검사와 유효한 모델 교정 제안, 등록 교정, 승인·일회 소비가 모두 있어야 실행한다. 첫 교정의 비회복 receipt를 검증한 뒤에만 두 번째 고리를 열며, 서로 다른 교정은 최대 두 건이다. 모델의 유효한 HOLD나 unknown 검사를 규칙 전환으로 우회하지 않는다. 계약·실행 조건은 [v2 사전등록](../bench/protocols/residual_demo_v2.json)에 고정했다.

| seed | 첫 검사·교정 | 첫 교정 평가 | 두 번째 검사·교정 | 최종 평가 | 검사 선택 주체 |
|---:|---|---|---|---|---|
| 2120 | `P_reward` abnormal · 보상 좌표계 복원 | `not_recovered` | `P_optimizer_updates` abnormal · PPO epoch 복원 | `recovered` | 두 번 모두 model |
| 2121 | `P_optimizer_updates` abnormal · PPO epoch 복원 | `not_recovered` | `P_reward` abnormal · 보상 좌표계 복원 | `recovered` | 두 번 모두 model |

모델이 정한 순서가 두 seed에서 달랐지만, 각 검사로 확정한 성분만 고친 뒤 남은 실패를 다시 진단했다. 각 arm은 4096환경·300회로 같은 seed에서 새로 학습했다. FIRST는 첫 교정만, BOTH는 누적된 두 교정을 적용했다.

| seed | 정상 NONE 수평 RMSE | 복합 결함 수평 RMSE | 첫 교정 FIRST 수평 RMSE | 두 교정 BOTH 수평 RMSE |
|---:|---:|---:|---:|---:|
| 2120 | 0.1413 m/s | 1.1780 m/s | 1.1756 m/s | 0.1413 m/s |
| 2121 | 0.1525 m/s | 1.2042 m/s | 1.1743 m/s | 0.1525 m/s |

고정 평가 26조건에서 두 FIRST는 비회복, 두 BOTH는 회복이었다. 여덟 arm의 생존 시간은 모두 20초, 낙상률은 모두 0이어서 이동 추종 지표가 판정을 갈랐다. BOTH와 NONE는 같은 seed의 정상 설정으로 새로 학습한 대조이며, 두 seed 모두 수평·yaw RMSE가 각각 같았다. [여덟 평가 기록](../evals/results/residual_success_public_20261017/evaluations/)

| 구분 | 결과 |
|---|---:|
| 진단 모델 첫 응답·최종 유효 | 각각 4/4 |
| 형식 유효 / 형식 유효 응답의 의미 유효 | 4/4 / 4/4 |
| 등록 규칙으로 검사 선택 전환 | 0/4 |
| 무효 진단 중 규칙 전환 | 해당 없음(무효 진단 0건) |
| 교정 모델 제안 유효 | 4/4 |
| 두 교정 뒤 종단 회복 | 2/2 |
| API 사용 | 8/20회 |

이번 실행에서 네 검사 선택은 모두 모델 응답이었고 피드백 재요청은 없었다. 규칙 전환 경로는 CPU fixture로 확인했으며 이번 GPU 실행에서는 사용되지 않았다. 따라서 회복 결과를 규칙 전환의 효과로 해석하지 않는다. 진단 유효율의 분모는 네 진단, 종단 회복률의 분모는 계획한 두 seed다. [모델·선택 기록](../evals/results/residual_success_public_20261017/model_audit.json)

학습·검사·평가 등 소유 프로세스 실행 구간의 합계는 4,168.154초이며 GPU 커널 시간이나 전체 lease 시간은 아니다. API는 총 15,639 token을 사용했다. [v2 비용](../evals/results/residual_success_public_20261017/costs.json) · [v1 비용](../evals/results/residual_failure_public_20261017_v2/costs.json)

설계자는 F1·R1 수리와 v1의 모델 계약 위반 결과를 본 뒤 v2를 만들었다. 두 seed는 사전등록 뒤 실행했지만 이 설계 결합을 가진 개발 측정이다. v1과 v2는 seed와 계약이 함께 바뀌었으므로, 이 결과만으로 계약 변경의 효과 크기를 분리하지 않는다.
