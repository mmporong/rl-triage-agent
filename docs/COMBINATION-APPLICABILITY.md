# 로봇·결함·교정 조합의 적용성 계약

등록된 결함과 교정이라도 로봇을 바꾸면 같은 방식으로 작동한다는 보장은 없다. 새 실행 경로는 실제 task의 표적, 주입 상태, 정책의 행동 실패, 교정 범위와 회복 방식을 차례로 검사한다. 이 관문을 통과한 `ready` 상태에서만 기존 교정 원장에 요청을 만든다.

`ready`는 교정을 요청할 조건을 갖췄다는 뜻이다. 정책이 회복했다는 판정은 교정 뒤 고정 평가에서 따로 내린다. 기존 실행기와 동결 검사 파일은 유지하고, 이 계약은 [새 조합 실행기](../evals/combination_trial_v1.py)에 연결했다.

## 관문과 중단 상태

| 순서 | 확인하는 근거 | 통과하지 못했을 때 |
| --- | --- | --- |
| 1. 적용성 | 주입 표적의 실제 경로, 활성 여부, 효과가 전달되는 경로 | `not_applicable` |
| 2. 주입 | 원본·주입 뒤 함수 지문, 활성 task와의 결합 | `invalid` |
| 3. 행동 실패 | 정상·결함 정책의 고정 평가, 기존 로봇별 밴드 | 정상 대조가 부적합하면 `baseline_invalid`, 행동 실패가 없으면 `source_failure_absent` |
| 4. 교정 범위 | 활성 표적 전체와 등록 교정 표적의 대응, 사용한 관측의 범위 | `scope_insufficient` 또는 근거 불완전 시 `invalid` |
| 5. NONE 대조 | 정상 함수에 같은 등록 교정을 적용한 전후 지문과 등록 밖 변경 | `invalid` |
| 6. 회복 방식 | 기존 등록 규칙과 요청 방식의 일치 | `invalid` |

원본 SHA나 관측과 manifest의 사실이 맞지 않아도 `invalid`다. 앞 관문에서 멈추면 뒤 관문을 호출하거나 결과를 생성하지 않는다. `not_applicable`, `source_failure_absent`, `scope_insufficient`는 모두 교정 요청 0건으로 끝난다. 계약의 제안 경로까지 들어온 입력은 원장에 HOLD 사유를 남긴다. 새 조합 실행기는 행동 실패가 없으면 계약·원장을 만들기 전에 종료한다.

보상 관측의 항별 범위는 기존 [`correction_scope.check`](../src/rl_triage/correction_scope.py)를 사용한다. 이 검사가 보는 두 추종 항과, 등록 주입이 바꾼 전체 표적은 별도로 확인한다. U1에서는 추종 항 두 개만 검사했더라도 네 보상 함수가 바뀌었다면 네 항 모두 교정 범위에 들어가야 한다.

이번 판에서 교정 요청까지 연결한 범주는 F1의 보상 항과 U1의 보상 함수군이다. F2·F6는 아래 기록의 선행 관문 상태를 재생한다. 이 두 범주의 입력이 교정 범위 관문까지 도달하면 범위 검사 미등록으로 `invalid`가 된다. 보상 검사 결과를 다른 범주의 확정 근거로 받아들이지 않는다.

## 기존 기록으로 만든 계약 회귀

아래 상태는 이미 본 기록을 새 계약에 넣은 개발 재생 결과다. 당시 실행기에 같은 상태명이 있었다는 뜻은 아니다. 원본 SHA를 고정한 정규화 도구와 공개 fixture로 상태를 재생한다.

| 사례 | 계약 상태 | 멈춘 위치 또는 확인한 범위 |
| --- | --- | --- |
| ANYmal-C F2 | `not_applicable` | LSTM 액추에이터의 실제 경로에서 F2 속도 배수 효과가 전달되지 않음 |
| ANYmal-C F6, seed 2100 | `source_failure_absent` | 종료 조건 주입은 확인됐지만 고정 평가에서 행동 실패가 없었음 |
| Go2 U1 구 교정, seed 2040 | `scope_insufficient` | 네 활성 항에 대해 단일 추종 항 복원만 등록됨 |
| Go2 U1 함수군 교정, seed 2062 | `ready` | 네 항 복원 범위와 NONE 무변경 근거가 있음 |
| Go2 F1, seed 2080 | `ready` | 단일 활성 표적 복원 범위와 등록 회복 방식이 일치함 |

U1 구 교정 재생은 seed 2040의 행동·관측과 seed 2062의 함수군 지문을 조합한 계약 개발 fixture다. 같은 seed의 추가 실험으로 세지 않는다. F1의 NONE 무변경 근거는 설치 소스의 격리 함수 객체에 `restore_body_frame_reward`를 적용한 별도 CPU 검사다. 정책 학습이나 행동 평가를 추가한 결과가 아니다.

공개 fixture는 원본 SHA를 보존하고 전체 파일 집합의 digest로 결합했다. manifest의 사실만 바꾸거나 관측·manifest·참조 SHA를 함께 바꿔도 검증을 통과하지 않는다. 회귀에서는 여섯 관문을 하나씩 제거해 해당 수용 조건이 실패하는지도 검사한다. 실행 코드에는 관문을 끄는 옵션이 없다.

## 고리와 교정 원장

호스트가 관측 원본으로 manifest를 구성하고 상태를 계산한다. 모델이나 호출자가 `ready`라는 문자열을 제공해 관문을 건너뛸 수 없다. 진단이 확정돼 있고 계약이 `ready`일 때만 등록 교정·회복 방식·전체 복원 표적을 기존 [`CorrectionLedger`](../src/rl_triage/correction_ledger.py)에 제안한다.

제안에는 manifest, 관측, 고리 상태와 등록 표의 digest가 묶인다. 승인을 한 번 소비하기 직전에 같은 근거로 관문을 다시 확인한다. 중복 제안, 승인 없는 실행, 중복 소비, 승인 뒤 근거 변경을 거부하며 결과는 기존 receipt 상태로 기록한다.

새 조합의 측정은 모델 판단 비교가 아니다. 등록 U1 입력의 함수 지문과 활성 표적 readback을 이용한 규칙 경로이며, 선택 주체는 `registered_rule`로 기록한다. 이 경로에서 기존 P_reward 검사를 실행한 것처럼 결과를 만들지 않는다.

## 사전등록한 새 조합

새 조합은 **ANYmal-C flat + U1 + 전체 보상 함수군 복원** 하나다. Go2에서 등록한 네 항 교정을 두 번째 로봇의 실제 활성 표적에 연결하는 계약을 확인하려고 골랐다. Go2 U1과 기존 ANYmal 결과를 본 뒤 설계했으며, 새 조합의 행동 결과는 아직 측정하지 않았다.

기존 ANYmal-C 밴드와 같은 고정 평가를 사용한다. 새 source seed 2150에서 NONE·U1 정책을 각각 300회 학습하고, 정상 대조가 유효하며 U1의 행동 실패가 확인된 경우에만 계약을 계속 평가한다. `ready`이면 seed 3150에서 네 항을 복원한 뒤 300회 재학습한다. NONE에 같은 교정을 적용했을 때의 무변경은 CPU 함수 지문으로 점검한다.

source failure가 없으면 그 결과로 종료한다. 실패 사례를 찾기 위해 다른 seed, 결함 크기나 평가 밴드를 탐색하지 않는다. 두 seed의 미사용 여부는 실행 직전에 다시 검사한다. 모델 API는 사용하지 않으며, GPU 실행은 커밋된 사전등록과 공용 lease가 갖춰진 메인 세션이 맡는다.
